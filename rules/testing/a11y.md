# Accessibility checks (axe-core, WCAG 2.2)

Locators and ARIA snapshots are in `testing/playwright`; Testing Library query order is in `testing/unit-js`; React Native accessibility props are in `mobile/react-native-expo`. This rule covers what accessible UI must do and how to check it.

## Version check

- Read `axe-core` and the integration you use (`@axe-core/playwright`, `jest-axe`, `cypress-axe`, `pa11y`) from the lockfile, and state them with the target level:

  ```text
  Applying testing/a11y (axe-core 4.14.0, @axe-core/playwright 4.14.0, target WCAG 2.2 AA, from pnpm-lock.yaml).
  ```

- **Target:** WCAG 2.2 Level AA for new work, unless the project or contract names another level. Legal baselines still cite WCAG 2.1 AA (the US ADA Title II rule, with compliance dates extended in Apr 2026 to 26 Apr 2027 and 26 Apr 2028; EN 301 549 under the European Accessibility Act, in force since 28 Jun 2025). 2.2 AA is a superset, so meeting it covers both.
- **axe-core 4.x** (4.14.0, Oct 2026): use tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` together; add `best-practice` only if the project already enforces it. Keep `@axe-core/*` packages on the same minor as `axe-core`.
- Below axe-core 4.10, or `jest-axe` that pins an old `axe-core`: update the integration rather than mixing versions.

## Conventions

### Build it accessible

- Native elements first: `<button>` for actions, `<a href>` for navigation, `<label for>` or wrapping labels for inputs, `<fieldset>`/`<legend>` for groups, `<table>` with `<th scope>` for data. Never put click handlers on `<div>` or `<span>`.
- ARIA only when no native element fits, and only per the ARIA Authoring Practices pattern for that widget (combobox, dialog, tabs, menu). Wrong ARIA is worse than none. Prefer the project's accessible primitives (Radix, React Aria, `@angular/aria`, Headless UI) over hand-rolled widgets; see `frontend/ui-shadcn-radix`.
- Every interactive element has an accessible name: visible text, a `<label>`, or `aria-label` for icon-only buttons. The visible label is part of the accessible name (2.5.3).
- Images: meaningful `alt` text; `alt=""` for decorative images. SVG icons inside labelled buttons get `aria-hidden="true"`.
- Forms: errors are text (not color only), linked with `aria-describedby`, announced (`aria-live="polite"` region or focus moved to an error summary), and set `aria-invalid="true"`. Required fields are marked in the label, not only with `*`. Use `autocomplete` tokens for personal data fields (1.3.5). See `frontend/forms-validation`.
- Keyboard: everything works with Tab, Shift+Tab, Enter, Space, Escape and arrow keys where the pattern says so. No `tabindex` above 0. No keyboard traps.
- Focus: always visible (don't remove outlines without a replacement), and not hidden behind sticky headers (2.4.11). Dialogs move focus in, trap it, close on Escape and return focus to the trigger. On client-side route changes, move focus to the new page heading or main region and update `document.title`.
- Structure: one `<h1>` per page, no skipped heading levels; landmarks (`<header>`, `<nav>`, `<main>`, `<footer>`); `lang` on `<html>`; a skip link on pages with repeated navigation.
- Color and size: text contrast ≥ 4.5:1 (3:1 for large text and UI component boundaries); pointer targets at least 24×24 CSS px or spaced (2.5.8); content reflows at 320 CSS px width and 200% zoom without loss.
- Motion: respect `prefers-reduced-motion`; nothing flashes more than three times a second; auto-playing or moving content can be paused.
- Dragging actions have a single-pointer alternative (2.5.7). Authentication doesn't rely on memory tests or puzzles without an alternative (3.3.8).

### Check it automatically

- **E2E (Playwright):** scan key pages and states (open dialogs, error states, logged-in views):

  ```ts
  import { test, expect } from '@playwright/test';
  import AxeBuilder from '@axe-core/playwright';

  test('checkout has no WCAG 2.2 AA violations', async ({ page }) => {
    await page.goto('/checkout');
    const results = await new AxeBuilder({ page })
      .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
      .analyze();
    expect(results.violations).toEqual([]);
  });
  ```

- **Cypress:** `cypress-axe` with `cy.injectAxe()` after `cy.visit()` and `cy.checkA11y(null, { runOnly: { type: 'tag', values: [...] } })`.
- **Component tests:** `jest-axe` (`expect(await axe(container)).toHaveNoViolations()`) in Jest; in Vitest, call `axe-core`'s `axe.run(container)` directly or use `jest-axe` with `expect.extend`. jsdom and happy-dom can't compute layout, so `color-contrast` is unreliable there: disable that rule in component tests only, and check contrast in a real browser.
- **Lint:** keep the framework's a11y lint on (`eslint-plugin-jsx-a11y`, `eslint-plugin-vuejs-accessibility`, the `@angular-eslint/template` accessibility rules, Svelte's built-in a11y warnings). Don't disable a rule inline without a reason in the summary.
- **Many URLs:** `pa11y` or `@axe-core/cli` against a preview deployment, if the project already runs them.
- **New pages fail on any violation.** On existing pages with a known backlog, fail on `serious` and `critical` impact, scope exceptions with `.exclude('<selector>')` or `.disableRules(['<rule-id>'])` per test with a linked issue, and never disable rules globally.
- Review `incomplete` results (axe's "needs review"); they aren't passes.

### Check it by hand

- Automated tools find only part of WCAG failures. For each changed screen, before you finish: tab through it with the keyboard only; zoom to 200%; and, for new widgets, check with a screen reader (VoiceOver on macOS/iOS, NVDA on Windows, TalkBack on Android). If you can't run one, list the manual checks for the user to do.

## Security

- Never add accessibility overlay or widget scripts that claim to make a site compliant. They don't fix the source, they inject third-party JavaScript with full DOM access on every page, and in 2025 the US FTC fined an overlay vendor $1 million over compliance claims. Fix the markup instead.
- Run checks against local, test or preview environments, not production with real user data. axe reports include HTML snippets; don't upload reports that contain personal data as public CI artifacts.
- Don't put secrets or personal data in `aria-label`, `title` or `alt`; screen readers, automation and analytics read them.
- Run `dependency-vet` before adding a11y test packages.

## Known vulnerabilities (as of 2026-11)

No current OSV advisories for `axe-core`, `@axe-core/playwright`, `jest-axe`, `cypress-axe` or `pa11y`. The browser drivers they run in have their own: Playwright before 1.55.1 installed browsers without TLS verification (CVE-2025-59288); see `testing/playwright`. This list goes stale; verify with the `cve-check` skill or OSV/GHSA before relying on it.

## Testing

- Prove the check can fail: remove a label or an `alt` once and confirm the axe test goes red.
- Cover states, not only the first render: open menus and dialogs, validation errors, empty and loading states, and dark mode if the app has one.
- Pair axe checks with `toMatchAriaSnapshot` for widgets whose structure and names matter (see `testing/playwright`).

## Before you finish

```sh
npx eslint .                                           # with the framework's a11y plugin enabled
npx playwright test --grep @a11y                       # or the project's a11y project/tag
npx vitest run --changed                               # component axe checks (or: npx jest --findRelatedTests <files>)
npx cypress run --spec "cypress/e2e/**/*a11y*"         # Cypress projects
npm ls axe-core @axe-core/playwright jest-axe          # one axe-core minor across integrations
npm audit --audit-level=moderate
```

Then report the manual keyboard, zoom and screen-reader checks you did, or the ones left for the user.
