# PostgreSQL

For Supabase projects also apply `data/supabase`; for NestJS ORMs also apply `backend/nestjs-data`. Generic injection and secrets rules are in `core/security-baseline`.

## Version check

- Find the server major: `select version();`, the Docker image tag, the managed-service setting, or `supabase/config.toml`. State it with the migration tool (raw SQL, Prisma, Drizzle, Sequelize, TypeORM, Flyway, …).
- Supported majors and latest minors (Oct 2026): 18.6, 17.11, 16.15, 15.19, **14.24 (EOL 12 Nov 2026)**. PostgreSQL 19 is at RC 1; don't target it unasked. Below 14 is unsupported: apply `core/legacy-mode` and say so in the summary.
- The next minor release is 12 Nov 2026. Recommend staying on the latest minor of the major in use.
- Version-gated features: `uuidv7()` needs 18; `MERGE … RETURNING` needs 17; `security_invoker` views and `NULLS NOT DISTINCT` need 15. Write SQL for the installed major.

## Conventions

### Naming

- New schemas: snake_case, unquoted identifiers (`order_items.created_at`). Existing schemas with quoted camelCase (`"createdAt"`) keep it; never mix styles in one schema (see `conventions/phaedra`).
- Follow the project's singular or plural table names. Name constraints and indexes predictably: `orders_customer_id_fkey`, `orders_status_check`, `orders_customer_id_idx`.
- ORM mapping: Prisma `@map("created_at")` and `@@map("orders")`; Drizzle `casing: 'snake_case'` or explicit column names.

### Types

- Timestamps: `timestamptz`, never `timestamp` without time zone. Store UTC; convert at the edge.
- Primary keys: `bigint generated always as identity` or `uuid` (`gen_random_uuid()`, or `uuidv7()` on 18 for index-friendly ordering). Not `serial`.
- Text: `text` with a `check (char_length(x) <= n)` when a limit matters. Money: `numeric(p, s)` or integer minor units, never `float` or `money`.
- Enum-like columns: a `check (status in (…))` or a lookup table. Use `create type … as enum` only for sets that never shrink.
- `jsonb` for genuinely schemaless data; promote fields you filter or join on to real columns.
- Prisma: `@db.Timestamptz(3)` on `DateTime`; Drizzle: `timestamp({ withTimezone: true })`.

### Constraints

- `not null` by default; allow null only where "unknown" is a real state.
- Foreign keys on every relationship, with an explicit `on delete` (`restrict`, `cascade` or `set null`) chosen per relationship.
- `unique` constraints for natural keys (`lower(email)` via a unique index), and `check` constraints for ranges and formats. Let the database enforce invariants; don't rely on application checks alone.

### Indexes

- Index every foreign-key column (Postgres doesn't do it automatically), and the columns used in `where`, `join`, `order by` and RLS policies.
- Composite indexes: equality columns first, then range or sort columns. Use partial indexes for hot subsets (`where deleted_at is null`).
- Check plans with `explain (analyze, buffers)` on realistic data before and after. Remove unused and duplicate indexes; each one slows writes.

### Migrations

- One migration per change, generated by the project's tool, reviewed as SQL, and committed. Never edit a migration that has run in any shared environment; add a new one.
- Provide a down migration or a written rollback plan when the tool supports it. Destructive steps (drop column, drop table, type change) go in a later release than the code that stops using them (expand, migrate, contract).
- Write migrations that are safe on large, busy tables:
  - set `lock_timeout` (for example `set lock_timeout = '5s';`) so a blocked `alter` fails instead of queueing all traffic;
  - `create index concurrently` (outside a transaction block) on existing tables;
  - add foreign keys and checks as `not valid`, then `validate constraint` in a separate step;
  - add `not null` to an existing column via a validated `check (col is not null)` first;
  - backfill in batches, not one `update` over the whole table;
  - adding a column with a constant default is cheap; changing a column's type rewrites the table.
- Never run `prisma db push`, `drizzle-kit push`, TypeORM `synchronize` or `sequelize.sync({ alter })` against shared databases. Use migrations.
- Run a migration linter (Squawk, or the project's) in CI when the project has one.

### Queries

- Select only the columns you need; no `select *` in application code.
- Paginate with `limit` plus keyset conditions for large tables; `offset` only for small ones.
- Avoid N+1 query loops; batch with `= any($1)` or joins.
- Keep transactions short; never hold one open across network calls.

## Security

- **Parameterize every value.** Use driver placeholders (`$1`), ORM bindings or tagged templates. Never concatenate or interpolate user input into SQL.
- Dynamic identifiers in PL/pgSQL: `format('select … from %I where id = %L', tbl, id)` or `quote_ident()`, and only for identifiers from an allowlist. `execute … using` for values.
- **Roles:**
  - The application connects as a dedicated login role that owns nothing and has only the `select`/`insert`/`update`/`delete` grants it needs. Migrations run as a separate owner role. Never connect the app as a superuser or the table owner.
  - On 14, run `revoke create on schema public from public;` (15+ does this by default).
  - Set `alter default privileges` so new tables get the app role's grants without broad `grant all`.
- **Row-level security** for multi-tenant tables: `enable row level security` plus `force row level security` (so the owner is also checked), with policies on `tenant_id = current_setting('app.tenant_id')::uuid` set per transaction with `set_config('app.tenant_id', $1, true)`. Never set it from unvalidated input.
- **Functions:** `security definer` only when required, with `set search_path = ''` (or `pg_catalog, pg_temp`), schema-qualified names, and `revoke execute … from public`. Functions get `execute` for `public` by default.
- **Connections:** TLS with certificate verification (`sslmode=verify-full`, or the driver's `ssl: { rejectUnauthorized: true, ca }`). Credentials come from a secret store, never from committed files or migration SQL.
- Behind PgBouncer in transaction mode, don't rely on session state (`set`, advisory locks, temporary tables) outside one transaction; use `set local` / `set_config(…, true)`.
- Don't log full SQL with bound parameters in production; it leaks PII and secrets.

## Known vulnerabilities (as of 2026-10)

| Advisory | Affected | Fixed |
|---|---|---|
| August 2026 release: 28 CVEs, including CVE-2026-16239 (cursor type confusion → code execution, CVSS 8.8), CVE-2026-15741 (SQL injection via `EXTRACT` deparse) and CVE-2026-19385 (`pg_dump` heap overflow) | 14–18 | 18.6, 17.11, 16.15, 15.19, 14.24 |
| CVE-2026-2006: multibyte length validation → arbitrary code execution | 14–18 | 18.2, 17.8, 16.12, 15.16, 14.21 (take 18.3/17.9/16.13/15.17/14.22 for the regression fix) |
| PostgreSQL 14 end of life | 14.x | No fixes after 12 Nov 2026; upgrade to 17 or 18 |

Several of these need only a normal database login, so patch even when the database isn't public. Client-side CVEs (`pg_dump`, `psql`) mean CI and developer tools need updating too. This list goes stale; verify with the `cve-check` skill or OSV/GHSA before relying on it.

## Testing

- Run migrations from zero and from the previous release's schema in CI against the same major as production (a container, not SQLite).
- Test constraints directly: invalid inserts fail with the expected constraint name.
- For RLS: test as the app role with two tenants and assert no cross-tenant reads or writes. Use pgTAP where the project has it.
- For slow-query fixes, record `explain (analyze, buffers)` before and after in the PR.

## Before you finish

```sh
npx prisma migrate reset --force && npx prisma validate   # Prisma, local database only: re-applies every migration
npx drizzle-kit check                                     # Drizzle: migration history is consistent
squawk migrations/*.sql                                   # if the project uses Squawk (squawk-cli)
psql "$LOCAL_DATABASE_URL" -v ON_ERROR_STOP=1 -f <migration>.sql   # raw SQL, local database only
npm test
```
